# 1.9 Update provider

Status: Done
Plan: [1.9 Update provider](../implementation-plan.md#19-update-provider)
Depends on: 1.5 booking policy, 1.6 venue details, 1.7 amenities, 1.8 admin create (all done)

## Goal
A profile created in 1.8 can be filled in and corrected: its basic info, venue details, booking policy and amenities, each saved on its own from one section of the editor. For now only admins can edit; 1.10 lets the provider's members use the same endpoints.

## Scope
- In: four command slices under `Application/Providers/` (`UpdateProviderBasicInfo`, `UpdateVenueDetails`, `UpdateBookingPolicy`, `UpdateProviderAmenities`), each with a validator and an endpoint in `Presentation/Providers/`; a `GetProviderForEditing` query (Dapper) and its endpoint; `Provider.ChangeBasicInfo`, sharing its checks with `Create`; `ProviderErrors.NotFound` and `ProviderErrors.ConcurrencyConflict`; `IAmenityRepository.GetByIdsAsync` with `AmenityErrors.NotFound`; optimistic concurrency on `providers` through `xmin`.
- Out: member access to these routes and the `ProviderMember`/`ProviderOwner` policies (1.10); the public page and its cache invalidation, `provider:{id}` (1.11 adds `RemoveByTagAsync` to these four handlers); edit locks while in review or suspended, and requiring details and a policy before review (1.13); moderation of name changes on published profiles (1.14); changing the category (not planned; P2.11 decides); changing the slug (never, 1.4); photos (3.3); offerings (1.15).

## Acceptance criteria
1. **Basic info**: a valid request replaces name, description, address, city, district, location and phone, sets `UpdatedAtUtc`, and returns `200 { version }`. Slug, category, status and claim stay as they were. The checks and errors of 1.8 apply unchanged (trimming, lengths, `Providers.DistrictRequired`, `Providers.DistrictNotInCity`, `Cities.NotFound`, `Districts.NotFound`, `Providers.LocationOutsideSerbia`, `Phones.InvalidNumber`); a blank phone or description clears it.
2. **Venue details**: a valid request sets `VenueDetails` and returns `200 { version }`; each `VenueDetails.*` error from 1.6 returns 400. On a non-venue provider the domain returns `Providers.VenueDetailsNotForCategory` (unit-tested; none exist until P2.11).
3. **Booking policy**: a valid request sets `BookingPolicy` and returns `200 { version }`; each `BookingPolicies.*` error from 1.5 returns 400.
4. **Amenities**: the request's list of amenity IDs replaces the set (an empty list clears it, a duplicate counts once) and returns `200 { version }`. An unknown ID fails with `Amenities.NotFound` (404) and nothing changes.
5. **Get for editing**: returns every editable field, the amenity IDs, status, slug, category, claimed flag and `version`, for any status. Booking policy and venue details are null while unset.
6. **Concurrency**: every update sends the `version` it last read. If the row changed since, the update fails with `Providers.ConcurrencyConflict` (409) and nothing is saved. The returned `version` is the new one, so the next update can be sent without reading again.
7. An unknown provider ID fails with `Providers.NotFound` (404) on all five endpoints.
8. Validators reject (400, `ValidationError`) an empty provider ID, the field rules of 1.8 for basic info, and an empty amenity ID in the list. A missing `version` or other required field is rejected by request binding (400).
9. Without a token all five return 401; a `Parent` or `ProviderMember` gets 403.

## API
Auth on all: `providers:manage-any` (1.10 adds membership as an alternative).
- `GET /providers/{providerId:guid}` → `200 { id, slug, name, category, description, address, cityId, districtId, latitude, longitude, phone, status, isClaimed, bookingPolicy, venueDetails, amenityIds, version }`.
- `PUT /providers/{providerId:guid}/basic-info`: `name`, `description?`, `address`, `cityId`, `districtId?`, `latitude`, `longitude`, `phone?`, `version`.
- `PUT /providers/{providerId:guid}/venue-details`: the ten fields of `VenueDetails.Create`, `version`.
- `PUT /providers/{providerId:guid}/booking-policy`: `depositType`, `depositValue?`, `depositDueDays?`, `freeCancellationDays`, `version`.
- `PUT /providers/{providerId:guid}/amenities`: `amenityIds`, `version`.
- Each `PUT` returns `200 { version }`. Errors: 400 `ValidationError` and the domain codes above; 404 `Providers.NotFound`, `Cities.NotFound`, `Districts.NotFound`, `Amenities.NotFound`; 409 `Providers.ConcurrencyConflict`; 401; 403.

## Data model
No new columns. `Provider` gets a shadow `Version` property mapped to Postgres `xmin` as its concurrency token (`IsRowVersion`, as `RefreshToken` does). The migration `AddProviderVersion` changes only the model snapshot.

## Edge cases
- Moving to another city keeps the slug (1.4); the district rule is checked against the new city. 1.11's canonical URL redirect covers the city change on the public page.
- A city that got districts after the provider was created: saving basic info then requires a district (1.3's edge case).
- An amenity update that changes nothing doesn't touch the `providers` row, so `version` stays the same and is returned unchanged.
- `ChangeAmenities` changes only `provider_amenities` rows, but it sets `UpdatedAtUtc` whenever the set changes, so the provider's `xmin` moves too and a concurrent edit is caught.

## Tests
- Unit: `ProviderTests` for `ChangeBasicInfo` (each check shared with `Create`, slug and category unchanged, `UpdatedAtUtc` set); a validator test class per command (AC 8 and the field rules).
- Integration (`UpdateProviderTests`, `GetProviderForEditingTests`, through HTTP as the seeded admin): each happy path read back through `GetProviderForEditing` (AC 1–5); city change with and without districts; unknown provider, city, district, amenity (AC 7, 4); a stale `version` gets 409 and leaves the row as it was (AC 6); two updates in a row using the returned `version`; 401 and 403 for a registered parent (AC 9). `ProviderPersistenceTests`: a row changed by another scope between load and save makes `IUnitOfWork.SaveChangesAsync` throw `ConcurrencyConflictException` and saves nothing (AC 6, the race path).

## Decisions
- **Four section endpoints, not one `PUT /providers/{id}`**: the plan names four commands, the editor saves one section at a time, and each reuses the validation of its value object.
- **Routes are `providers/{providerId}/...`, not `/admin/providers/...`**, so 1.10 only adds a policy; the admin and the owner share one editor and one API.
- **Admin-only through `providers:manage-any` until 1.10**, the permission the `Admin` role already has.
- **Category isn't editable**: details, amenities and (later) offerings depend on it.
- **Each section replaces its whole value**; policy and details can be replaced but not cleared, since 1.13 requires them before review.
- **`version` goes in the request body, not `If-Match`**: simpler for the Angular client, and the response body carries the new one.
- **The version is a shadow property, kept out of Domain**; `IProviderRepository.GetVersion(provider)` reads it, and a version that doesn't match on load returns `Providers.ConcurrencyConflict` at once. A change in the moment between load and save surfaces as EF's `DbUpdateConcurrencyException`; `KidsPartyVenueDbContext.SaveChangesAsync` rethrows it as an Application-level `ConcurrencyConflictException`, which the handlers turn into the same error, so Application never references EF.
- **`ChangeBasicInfo` takes the same inputs as `Create`** (loaded `District?` and `cityHasDistricts`), and the handler loads them as 1.8 does; the shared checks move to one private method in `Provider`.
- **No cache invalidation now**: nothing caches a provider until 1.11.

- **Optimistic concurrency comes now** (owner's answer), as 1.3 left it to 1.9: an admin and, after 2.8, the owner can edit the same profile, and without it the later save silently overwrites the earlier one.
- **The editor's `GET /providers/{providerId}` comes in this step** (owner's answer): no other step reads a Draft for editing (1.11 is public and published only, 7.2 is a list), and the editor needs the current values and `version`. The `:guid` constraint keeps it apart from 1.11's `GET /providers/{slug}`.
- **The city can be changed, in any status, and the slug stays** (owner's answer); 1.13 or 1.14 can restrict it on published profiles if needed.
- **Edits are allowed in every status, including `PendingReview` and suspended** (owner's answer); 1.13 decides the locks together with the workflow.

- **Found during the build:** the migration is `AddProviderVersion`; it only records the model change, because Npgsql emits no SQL for the `xmin` system column. The explicit `IUnitOfWork.SaveChangesAsync` on the context does the exception translation, so `IdentityService`, which saves the context directly, still catches EF's exception for refresh tokens. A missing `version` (or other required field) is rejected by request binding with a plain 400, as in 1.8, not by the validators. The venue details and booking policy validators check only the provider ID, so their ranges come back with the domain's error codes. `Provider.Create` now checks the category before the name, because the shared checks run after it; that only changes which error comes first when several are wrong. The query reads `xmin` as `xmin::text::bigint`, since `xid` has no direct cast to `bigint`.
