# 1.13 Review workflow

Status: Done
Plan: [1.13 Review workflow](../implementation-plan.md#113-review-workflow)
Depends on: 1.3 provider entity (status and `SuspendedAtUtc` exist), 1.9 update provider, 1.10 membership policy, 1.11 visibility rule, 1.12 self-registration (all done)

## Goal
A profile goes public only after an admin has checked it. The owner (or the admin, for an unclaimed profile) submits a complete profile, the admin publishes it or sends it back with notes, and the admin can suspend and unsuspend any profile.

## Scope
- In: domain methods `SubmitForReview`, `Approve`, `RequestChanges`, `Suspend`, `Unsuspend` on `Provider`; the completeness check before review; the edit lock while `PendingReview`; five command slices (`Application/Providers/{SubmitProviderForReview,ApproveProvider,RequestProviderChanges,SuspendProvider,UnsuspendProvider}/`) with endpoints; review notes, suspension reason and the review timestamps on `providers`; these fields in 1.9's editor read and the suspended flag in 1.12's `GET /users/me/providers`.
- Out: the admin review queue and provider list (7.1, 7.2); emails about the result and the confirmed-email requirement (2.6 templates, sent through the outbox of M2; the domain events come with 2.1); who did what and the history of earlier notes (1.14 audit log); moderation of name changes and new media on published profiles (1.14, 3.3); an owner unpublishing or deleting their profile (not planned); opening a city category (7.7).

## Acceptance criteria
1. **Submit**: `Draft` or `ChangesRequested` → `PendingReview`, sets `SubmittedAtUtc` and `UpdatedAtUtc`. Any other status: 409 `Providers.NotSubmittable`.
2. **Complete before review**: submit fails with 400 when the booking policy is missing (`Providers.BookingPolicyRequired`), a venue has no venue details (`Providers.VenueDetailsRequired`) or the phone is missing (`Providers.PhoneRequired`), checked in that order. Amenities and description stay optional.
3. **Approve**: `PendingReview` → `Published`, sets `ReviewedAtUtc`, clears `ReviewNotes`. Any other status: 409 `Providers.NotPendingReview`. Approving in a city whose venue category isn't open works; the profile turns visible when it opens.
4. **Request changes**: `PendingReview` → `ChangesRequested` with required notes (trimmed, 1–2000 chars; `Providers.ReviewNotesRequired`, `Providers.ReviewNotesTooLong`, 400), sets `ReviewedAtUtc`. Other status: 409 `Providers.NotPendingReview`.
5. **Edit lock**: while `PendingReview`, the four 1.9 updates return 409 `Providers.InReview`, for owners and admins alike. In every other status, suspended included, they work as before.
6. **Suspend**: sets `SuspendedAtUtc` and a required reason (trimmed, 1–1000 chars; `Providers.SuspensionReasonRequired`, `Providers.SuspensionReasonTooLong`), keeps the status. Already suspended: 409 `Providers.AlreadySuspended`. **Unsuspend** clears both; not suspended: 409 `Providers.NotSuspended`. Workflow transitions still work while suspended.
7. Every transition takes the `version` from the last read, returns the new one, and gives 409 `Providers.ConcurrencyConflict` on a stale version, as 1.9 does.
8. Approve, suspend and unsuspend remove `provider:{id}` after the commit: a published profile shows up on 1.11's page on the next request, and disappears when suspended.
9. `GET /providers/{providerId}` (editor read) adds `reviewNotes`, `submittedAtUtc`, `reviewedAtUtc`, `suspendedAtUtc`, `suspensionReason`. `GET /users/me/providers` adds `isSuspended`.
10. Auth: submit uses the `ProviderMember` policy (owner or admin; 403 rules of 1.10). Approve, request changes, suspend and unsuspend need `providers:review`: an owner gets 403, no token 401, an unknown ID 404 `Providers.NotFound`.

## API
All return `200 { version }`; errors as in the criteria plus 400 `ValidationError`, 401, 403, 404 `Providers.NotFound`.
- `POST /providers/{providerId}/submit`, `ProviderMember`, body `{ version }`.
- `POST /admin/providers/{providerId}/approve`, `providers:review`, body `{ version }`.
- `POST /admin/providers/{providerId}/request-changes`, `providers:review`, body `{ notes, version }`.
- `POST /admin/providers/{providerId}/suspend`, `providers:review`, body `{ reason, version }`.
- `POST /admin/providers/{providerId}/unsuspend`, `providers:review`, body `{ version }`.

## Data model
`providers` gets, all nullable: `review_notes varchar(2000)`, `submitted_at_utc timestamptz`, `reviewed_at_utc timestamptz`, `suspension_reason varchar(1000)`. Check constraint `ck_providers_suspension`: `suspended_at_utc` and `suspension_reason` are both null or both set. An index on `(status, submitted_at_utc)` waits for the queue (7.1).

## Edge cases
- An admin-created, unclaimed profile: the admin submits and approves it; it can be public before it is claimed (2.8).
- Resubmitting after changes keeps the old notes visible until the next decision.
- A published profile edited by its owner stays published; 1.14 moderates name and media changes.
- Two admins decide on the same profile at once: the second gets `Providers.ConcurrencyConflict`.
- A suspended profile that is approved stays hidden until unsuspended.

## Tests
- Unit (`ProviderReviewTests`): every allowed and rejected transition (AC 1, 3, 4, 6); each missing requirement and its order (AC 2); notes and reason trimming and length bounds. Validator tests for the notes and reason commands.
- Integration (`ProviderReviewWorkflowTests`, through HTTP): owner submits, admin approves, the public page returns it (AC 1, 3, 8); request changes, resubmit, approve (AC 4); incomplete profile (AC 2); each 1.9 update returns `Providers.InReview` while pending and works after (AC 5); suspend hides the public page, unsuspend shows it (AC 6, 8); stale version (AC 7); editor read and my-providers fields (AC 9); owner 403 on admin routes, another owner 403 on submit, 401, admin 404 (AC 10). `ProviderPersistenceTests`: the new columns and the suspension check constraint. `GetPublicProviderTests` can switch from direct SQL to the commands.

## Decisions
- **Admin routes under `admin/providers/...`**, like 1.8's create; submit sits with the owner routes under `providers/{providerId}`.
- **One action endpoint per transition**, not a `PUT status`: each has its own rules, body and permission.
- **Only the latest notes are stored on `providers`**: the history of decisions and who made them comes from the audit log (1.14), so no review table yet.
- **Suspension uses `providers:review`**, not `providers:manage-any`: the same admin role, and it's moderation. Only `Admin` has both today.
- **Edits on a published profile go live without a new review**; 1.14 covers the risky ones (name, media).
- **No withdraw (PendingReview → Draft)**: the admin can request changes instead; can be added later if owners need it.

- **Edits are locked while `PendingReview`** (owner's answer): the admin approves exactly what was submitted.
- **The phone is required before review** (owner's answer): it's public (1.11) and the only direct contact until inquiries exist (M5).
- **The admin can't approve a `Draft` directly** (owner's answer): for an unclaimed profile the admin calls submit, then approve, so there is one path and one completeness check.
- **A suspension reason is required** (owner's answer): it's shown to the owner in the editor read, so they know what to fix.

- **Found during the build:** the edit lock lives in the domain (each `Change*` method returns `Providers.InReview`), so `ChangeBookingPolicy` now returns `Result` like the others. Approve, suspend and unsuspend remove `provider:{id}`; submit and request changes don't, since the profile isn't public before or after. The validators check only the provider ID, so the domain's notes and reason codes reach the client. The migration is `AddProviderReview`. `GetPublicProviderTests` still sets status directly to stay about visibility, and its direct suspension now sets a reason to satisfy `ck_providers_suspension`.
