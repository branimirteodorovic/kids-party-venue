# 1.1 Cache tags

Status: Done
Plan: [1.1 Cache tags](../implementation-plan.md#11-cache-tags)
Depends on: none (HybridCache and `ICacheService` exist since the template)

## Goal
Cached reads can be grouped under tags and dropped together, so a write invalidates every entry it affects without knowing their keys. The first users are the provider page (1.11, tag `provider:{id}`), the catalogs (1.2) and cached memberships (1.10).

## Scope
- In: an optional `tags` parameter on `ICacheService.GetOrCreateAsync` and `SetAsync`, a new `ICacheService.RemoveByTagAsync`, both passed through to HybridCache tags in `CacheService`; the tag naming convention in the coding-style rule and `Backend/CLAUDE.md`.
- Out: tag helpers for specific areas, such as `provider:{id}` (added by the step that caches them: 1.2, 1.10, 1.11); caching permissions (1.10); a distributed L2 cache or backplane for more than one API instance (not planned; one VPS per environment).

## Acceptance criteria
1. `GetOrCreateAsync` and `SetAsync` take an optional `IEnumerable<string>? tags`; existing calls without tags compile and behave as before.
2. After `RemoveByTagAsync("t")`, `GetOrCreateAsync` for an entry tagged `t` runs its factory again and returns the new value.
3. An entry with several tags is invalidated when any one of them is removed.
4. Entries without the removed tag keep their cached value.
5. An entry created with the tag after `RemoveByTagAsync` is cached normally (the removal doesn't affect later entries).
6. Removing a tag that no entry has is a no-op and doesn't throw.
7. `RemoveAsync(key)` still removes a single entry, tagged or not.
8. A null, empty or whitespace tag, or the tag `*`, throws `ArgumentException`, both when tagging an entry and when removing a tag. (`*` means "everything" to HybridCache, so it must never be used by accident.)

## API
None.

## Data model
No change.

## Edge cases
- A factory still running when its tag is removed may store a value read before the write. Writers invalidate only after `SaveChangesAsync` succeeds, so at most one request sees stale data until the next invalidation or expiration.
- Tags are case-sensitive (`provider:x` and `Provider:x` are different); the naming convention keeps them lowercase.
- Invalidation is in-process only. That is correct for one API instance and must be revisited if the API is ever scaled out.

## Tests
- Integration (`tests/KidsPartyVenue.IntegrationTests/Caching/CacheServiceTests.cs`), resolving `ICacheService` from the test host so the DI wiring is covered too. Each test uses its own random keys and tags, because the cache is shared by the test collection:
  - criteria 2 to 7, each with a factory that counts its calls
  - `SetAsync` with a tag, then `RemoveByTagAsync`, then `GetOrCreateAsync` runs the factory
  - criterion 8 as a theory over `null`, `""`, `" "` and `*`, for `GetOrCreateAsync`, `SetAsync` and `RemoveByTagAsync`

## Decisions
- **One tag per `RemoveByTagAsync` call**, as the plan names it. A write that touches several tags calls it once per tag; an overload for many can be added when a handler needs it.
- **No "clear everything" method.** Nothing needs it, and `*` is rejected so it can't happen by mistake.
- **Tags mirror the key convention**: `"<area>:<id>"`, lowercase, for example `provider:{id}` or `city:{id}`. Written into the Caching section of `.claude/rules/backend-coding-style.md` and the Caching line of `Backend/CLAUDE.md`.
- **Invalidate in the command handler, after `SaveChangesAsync`.** Never before the commit, or a concurrent read can cache the old row again. A later step can move this to the outbox (M2) if invalidations multiply.
- **`tags` is `IEnumerable<string>?`**, the type HybridCache takes, and sits after `expiration` and before `cancellationToken`, so existing calls stay valid.
- **Tested through integration tests, not unit tests.** `CacheService` is internal to Infrastructure, which the unit test project doesn't reference, and the real HybridCache is what needs checking.
- **Permissions are cached in 1.10, not here.** The plan said 0.6d caches role permissions, but `PermissionService` queries the database on every authenticated request. Nothing can change a user's roles yet, so there would be nothing to invalidate. 1.10 caches them with memberships under a `user:{id}` tag, and the plan now says so.
