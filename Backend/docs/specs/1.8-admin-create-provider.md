# 1.8 Admin: create provider

Status: Done
Plan: [1.8 Admin: create provider](../implementation-plan.md#18-admin-create-provider)
Depends on: 0.6 identity (done, the `providers:create` permission on `Admin`), 1.3 provider entity, 1.4 slug generation (done)

## Goal
An admin can add a venue they know about, in any city, before its owner has an account. The profile starts as an unclaimed Draft; 1.9 fills in the rest, 2.8 lets the owner claim it, and 1.13 publishes it.

## Scope
- In: `CreateProviderCommand` with its handler and validator (`Application/Providers/CreateProvider/`), the `POST /admin/providers` endpoint (`Presentation/Providers/CreateProvider.cs`, tag `Providers`), `ICityRepository.ExistsAsync` and `IDistrictRepository` (`GetByIdAsync`, `AnyInCityAsync`) with their Infrastructure implementations, and new `CityErrors.NotFound` and `DistrictErrors.NotFound`.
- Out: booking policy, venue details and amenities (1.9, the same commands for admins and owners); memberships and an owner (1.10, 1.12, 2.8 claim); an admin `GET` for the new profile (7.2 list; the public page 1.11 shows only published ones); the review workflow (1.13); the audit entry (1.14 records every write through its interceptor); other categories (P2.11); photos (M3).

## Acceptance criteria
1. A user with `providers:create` posts a valid request and gets `201` with the new provider's `id` and `slug`. The saved provider is `Draft`, unclaimed (`ClaimedAtUtc` null), with no booking policy, venue details or amenities, and `CreatedAtUtc = UpdatedAtUtc = now`.
2. The slug comes from the name through `IProviderSlugGenerator`: a second provider with the same name gets `-2`. The request has no slug field.
3. Any city works, hidden or with venues closed.
4. In a city that has districts, a district from that city is required: none fails with `Providers.DistrictRequired`, one from another city with `Providers.DistrictNotInCity` (both 400). In a city without districts, the district is omitted.
5. An unknown city fails with `Cities.NotFound`, an unknown district with `Districts.NotFound` (404). Nothing is saved.
6. The validator rejects (400, `ValidationError`): an empty or too long name or address, a too long description, a category other than `Venue`, an empty city ID, and latitude or longitude out of range. The domain rejects a location outside Serbia (`Providers.LocationOutsideSerbia`) and an invalid phone (`Phones.InvalidNumber`).
7. The phone is optional; when given, it's stored in E.164 (`063 123 4567` → `+381631234567`). A blank description is stored as null.
8. Without a token the endpoint returns 401; a `Parent` or `ProviderMember` gets 403.

## API
`POST /admin/providers`, auth: `providers:create`.
- Request: `name`, `category` (`"Venue"`), `description?`, `address`, `cityId`, `districtId?`, `latitude`, `longitude`, `phone?`.
- Response: `201 Created`, body `{ id, slug }`, no `Location` header (no admin `GET` exists until 7.2).
- Errors: 400 `ValidationError` and the `Providers.*`, `Phones.InvalidNumber`, `Geography.InvalidCoordinate` codes above; 404 `Cities.NotFound`, `Districts.NotFound`; 401; 403.

## Data model
No change.

## Edge cases
- Two creates with the same name at the same moment: the unique slug index rejects one with a 500 that can be resent (1.4's decision, unchanged).
- Coordinates inside Serbia but far from the chosen city aren't checked; the admin places the pin on the city's map.
- A district given for a city without districts fails as `Providers.DistrictNotInCity`, since it belongs to another city.

## Tests
- Unit (`CreateProviderCommandValidatorTests`): each rule in AC 6, and a valid command passes.
- Integration (`CreateProviderTests`, through HTTP as the seeded admin): the happy path read back through `IProviderRepository` (AC 1, 7); slug suffix on a repeated name (AC 2); a hidden city (AC 3); district required, wrong city, omitted where none exist (AC 4); unknown city and district (AC 5); category `Catering`, outside Serbia, bad phone (AC 6); 401 and 403 for a registered parent (AC 8).

## Decisions
- **Create takes basic info only.** Booking policy, venue details and amenities go through 1.9's commands, so their validation lives in one place for admins and owners.
- **One command for admin create now; 1.12 adds its own** (`RegisterProviderCommand`), because it also creates the Owner membership and needs a different permission. The shared lookup of city and district can move to a helper then.
- **The `Venue`-only rule is in the validator**, as 1.3 decided, so P2.11 only changes the validator.
- **Lookups go through new repositories** (`ICityRepository`, `IDistrictRepository`): commands use repositories, not Dapper. Districts are their own entity (own `DbSet`), so they get their own repository.
- **No cache invalidation**: a Draft isn't public and nothing caches it; the catalogs don't count providers.
- **The route is `/admin/providers`** as in the plan, with the `Providers` tag; the admin API in M7 adds more under `/admin`.

- **An unknown city or district is 404** (owner's answer), with `Cities.NotFound` / `Districts.NotFound`, so the frontend can tell "not found" from a form error and 1.9 and 1.12 can reuse the codes.
- **No duplicate warning** (owner's answer): the slug suffix keeps both valid, and 7.2's list with filters lets the admin spot one. It can come later if it happens in practice.

- **Found during the build:** the unit test project now references Application, which grants it `InternalsVisibleTo`, so internal validators can be unit-tested. The handler counts the city's districts only when no district is given; a given district already answers it.
