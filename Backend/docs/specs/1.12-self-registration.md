# 1.12 Self-registration

Status: Done
Plan: [1.12 Self-registration](../implementation-plan.md#112-self-registration)
Depends on: 0.6 identity (done, `providers:register` on `Parent` and `ProviderMember`), 1.8 admin create, 1.10 provider membership (done)

## Goal
A venue owner who signed up on the site creates their own profile. It starts as a claimed Draft with them as its Owner, so the editor endpoints of 1.9 open to them right away; 1.13 then takes it through review.

## Scope
- In: `RegisterProviderCommand` with its handler and validator (`Application/Providers/RegisterProvider/`); the `POST /providers` endpoint (`Presentation/Providers/RegisterProvider.cs`, tag `Providers`); `IIdentityService.EnsureProviderMemberRoleAsync`; a shared `ProviderPlaceLookup` in `Application/Providers/` (city exists, district found, city has districts), used by 1.8's create, 1.9's basic-info update and this step; the `GetMyProvidersQuery` with its handler and response (`Application/Providers/GetMyProviders/`) and the `GET /users/me/providers` endpoint (`Presentation/Providers/GetMyProviders.cs`, tag `Providers`).
- Out: booking policy, venue details and amenities (1.9's commands, now open to the new owner); submitting for review, review notes and requiring a confirmed email (1.13, once M2 sends the mail); the audit entry (1.14); claiming an admin-created profile (2.8); co-owners and staff (2.8, P2.16); other categories (P2.11); photos (M3); a limit on registrations per user (later, if abuse shows up).

## Acceptance criteria
1. A user with `providers:register` posts a valid request and gets `201` with `{ id, slug }` and `Location: /providers/{id}`. The saved provider is `Draft`, claimed (`ClaimedAtUtc = CreatedAtUtc = UpdatedAtUtc = now`), with no booking policy, venue details or amenities.
2. The caller is the provider's only member, as `Owner`, with `JoinedAtUtc = now`.
3. The caller gets the Identity role `ProviderMember` and keeps `Parent`. A user who already has `ProviderMember` (a second provider) registers without error and keeps one copy of the role.
4. After the call, the same access token can read `GET /providers/{id}` and update it through 1.9's endpoints: the `user:{id}` cache tag is removed after the commit, so memberships and permissions are read again.
5. Provider, membership and role are saved in one transaction: when any part fails, none is saved.
6. Slug, city, district, phone and validation behave as in 1.8 (AC 2–7 there), with the same error codes: any city works, hidden or with venues closed; `Providers.DistrictRequired`, `Providers.DistrictNotInCity` (400); `Cities.NotFound`, `Districts.NotFound` (404); `ValidationError`, `Providers.LocationOutsideSerbia`, `Phones.InvalidNumber` (400); only `Venue` is accepted.
7. Without a token: 401. A user without `providers:register` (today: `Admin`) gets 403.
8. 1.8's admin create and 1.9's basic-info update behave as before after the lookup moves to `ProviderPlaceLookup` (their existing tests pass unchanged).
9. `GET /users/me/providers` returns the caller's providers, oldest membership first, each with `id`, `slug`, `name`, `status` and `role`. A user with none (a parent, the admin) gets an empty list. Another owner's providers never appear. Without a token: 401.

## API
`POST /providers`, auth: `providers:register`.
- Request: the 1.8 body: `name`, `category` (`"Venue"`), `description?`, `address`, `cityId`, `districtId?`, `latitude`, `longitude`, `phone?`.
- Response: `201 Created`, `Location: /providers/{id}` (the 1.9 editor read), body `{ id, slug }`.
- Errors: 400 `ValidationError`, `Providers.*`, `Phones.InvalidNumber`, `Geography.InvalidCoordinate`; 404 `Cities.NotFound`, `Districts.NotFound`; 401; 403.

`GET /users/me/providers`, auth: `users:read-self`.
- Response: `200 OK`, a list of `{ id, slug, name, status, role }`, no paging.
- Errors: 401.

## Data model
No change. The provider goes into `providers`, the Owner into `provider_members` (1.10), the role into `identity.user_roles`.

## Edge cases
- One user registers several providers (one per category later): each gets its own Owner membership; the role is assigned once.
- The token's user no longer exists: role assignment fails with `Users.NotFound` (404) and nothing is saved.
- Two registrations with the same name at the same moment: one fails on the unique slug index with a 500 that can be resent (1.4, unchanged).
- A registered owner also books parties for their own kids: keeping `Parent` keeps that working.

## Tests
- Unit (`RegisterProviderCommandValidatorTests`): the 1.8 rules, and a valid command passes.
- Integration (`RegisterProviderTests`, through HTTP as a newly registered parent): happy path read back through `IProviderRepository` with the Owner member and `ClaimedAtUtc` (AC 1, 2); roles after one and after two registrations (AC 3); the same token reads and updates the new provider right after, with memberships warmed in the cache before the call (AC 4); a failing provider insert after the role is saved leaves neither the provider nor the role (AC 5, with a throwing `IProviderRepository`); an unknown city leaves the role unchanged; hidden city, district rules, unknown city and district, `Catering`, outside Serbia (AC 6); 401, and 403 for the seeded admin (AC 7). The existing `CreateProviderTests` and `UpdateProviderTests` cover AC 8.
- Integration (`GetMyProvidersTests`): an owner of two providers gets both in order with their status and role, not another owner's; a parent and the admin get an empty list; 401 (AC 9).

## Decisions
- **A separate command from 1.8's create**, as 1.8 decided: it needs a different permission, the Owner membership, the role and a transaction.
- **The provider is created claimed** (`isClaimed: true`): its owner made it, so "claimed" (1.3: an owner runs it) is true from the start; 2.8 only claims admin-created ones.
- **The route is `POST /providers`**, next to `GET /providers/{providerId}` that `Location` points to; the public `GET /providers/{slug}` doesn't conflict (different method).
- **The role goes through a new `IIdentityService.EnsureProviderMemberRoleAsync`**, idempotent, so Application stays free of `UserManager`. It runs inside the handler's transaction, like `RegisterAsync` in 0.6b.
- **The user keeps `Parent`**: roles add up, and an owner can still book as a parent.
- **Admins don't self-register** (no `providers:register`): they use `POST /admin/providers` for unclaimed profiles.
- **The place lookup moves to `ProviderPlaceLookup`** now that three handlers need it (1.8's note).
- **The phone stays optional**, as in 1.8; 1.13 can require it for review.
- **Only `user:{id}` is invalidated**: the Draft isn't public, so no `provider:{id}` entry exists yet.

- **No limit on registrations per user** (owner's answer): Drafts are invisible and review (1.13) gates publishing, so spam stays out of sight. A limit (for example open Drafts per user) can come if abuse shows up.
- **`GET /users/me/providers` is part of this step** (owner's answer): the panel needs it after the next login to find the provider's ID, and 1.12 is where a user first gets a provider. It's a Dapper read joining `provider_members` and `providers`, not cached: it runs once when the panel opens.
- **No confirmed email required** (owner's answer): no confirmation mail exists before M2; 1.13's submit-for-review can require it once M2 sends the mail.

- **Found during the build:** the role is assigned before the provider is inserted, because `UserManager` saves the context on its own; the transaction rolls the role back when the provider fails. AC 5 is tested that way (a throwing `IProviderRepository`), which proves more than a failing role, since nothing is inserted before the role. `ProviderPlaceLookup` sits behind `IProviderPlaceLookup` and returns a `ProviderPlace` (district, whether the city has districts), registered next to the slug generator. The message of `Users.RoleAssignmentFailed` no longer says "default role", since it now covers `ProviderMember` too; the code is unchanged.
