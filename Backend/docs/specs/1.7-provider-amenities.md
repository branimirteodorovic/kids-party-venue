# 1.7 Provider amenities

Status: Done
Plan: [1.7 Provider amenities](../implementation-plan.md#17-provider-amenities)
Depends on: 1.2 lookup data (done, the `amenities` table and seed), 1.3 provider entity (done)

## Goal
A venue can be marked with the amenities it has (parking, ball pit, and so on) from the seeded list. 1.9 lets providers choose them, 1.11 shows them on the page, 3.5 filters search by them, and P3.7 points out the ones a provider hasn't marked.

## Scope
- In: the `ProviderAmenity` child entity inside the `Provider` aggregate, `Provider.Amenities` and `Provider.ChangeAmenities`, new `ProviderErrors`, the `provider_amenities` table with its keys and index, loading the amenities with the provider, and the migration.
- Out: the command, endpoint and amenity lookup by IDs that set them (1.9, which adds `IAmenityRepository` if it needs one); showing them, sorted by `Amenity.SortOrder` and named in the request language (1.11); the search filter and any extra index it needs (3.5); adding, renaming or retiring amenities, and what happens to providers that use a retired one (7.6); amenities for other categories (P2.11); development sample providers (1.11).

## Acceptance criteria
1. `Provider.Create` leaves `Amenities` empty.
2. `Provider.ChangeAmenities(amenities, utcNow)` on a `Venue` provider replaces the set with the given amenities: the new ones are added, the missing ones removed, the ones in both kept. It sets `UpdatedAtUtc` when the set changed and leaves it alone when it didn't.
3. An empty collection clears the set. The same amenity given twice is stored once.
4. On a provider whose category isn't `Venue`, `ChangeAmenities` fails with `Providers.AmenitiesNotForCategory` and changes nothing.
5. A provider saved with amenities is read back through `IProviderRepository.GetByIdAsync` with the same amenity IDs, without the caller asking for them. Changing the set on a tracked provider loaded in a new scope saves exactly the added and removed rows.
6. The database rejects a row for an amenity that doesn't exist (foreign key), a duplicate `(provider_id, amenity_id)` (primary key), and deleting an amenity that a provider uses (restrict). Deleting a provider deletes its rows (cascade).

## API
None.

## Data model
- `provider_amenities`: `provider_id uuid` FK to `providers` (cascade); `amenity_id uuid` FK to `amenities` (restrict); PK `(provider_id, amenity_id)`; index on `amenity_id` (the restrict check, and 3.5's filter "venues that have amenity X").
- No change to `providers` or `amenities`.

## Edge cases
- `Catering` and `Cakes` exist in `ProviderCategory`, but nothing creates them until P2.11; they get no amenities, the same rule as venue details (1.6).
- An amenity that exists but is retired later (7.6) stays on the providers that have it; 7.6 decides whether retiring removes it or hides it.
- The seed has 13 amenities, so the set needs no size limit; marking all of them is valid.

## Tests
- Unit (`ProviderTests`): empty after create; `ChangeAmenities` adds, removes and keeps; changes `UpdatedAtUtc` only when the set changed; an empty collection clears; a duplicate is stored once; fails with `Catering` and `Cakes` and leaves the set and `UpdatedAtUtc` unchanged; throws on null.
- Integration (`ProviderPersistenceTests`): the round trip with seeded amenities through `GetByIdAsync` in a new scope; changing the set on a provider loaded tracked in a new scope (one kept, one added, one removed); the unknown amenity, duplicate row and amenity delete rejected with their Postgres codes; deleting a provider removes its rows.

## Decisions
- **A child entity `ProviderAmenity (ProviderId, AmenityId)` inside the `Provider` aggregate, like `CityCategory` in `City`.** The provider refers to an amenity by ID only, so the `Amenity` lookup entity stays outside the aggregate; an EF skip navigation to `Amenity` would put it inside.
- **`ChangeAmenities` takes `Amenity` entities, not IDs**, like `Provider.Create` takes a `District`: the caller has to load them, so an unknown ID fails in the handler (1.9) with a clear error instead of at the foreign key.
- **One method that replaces the set, not add and remove**: the editor (1.9) sends the whole list of checkboxes. Diffing keeps unchanged rows, so nothing is deleted and inserted again.
- **The amenities always load with the provider** (`AutoInclude`): they are part of the aggregate and only a handful of rows, so a handler can't forget them and save a wrong diff.
- **Amenities aren't required before review** (1.13): having none is a valid answer.
- **No extra cache tag now**: nothing caches a provider until 1.11, which invalidates `provider:{id}` on every profile write.

- **Only venues have amenities until P2.11** (owner's answer): the seeded list is venue amenities, so other categories fail with `Providers.AmenitiesNotForCategory`. P2.11 lifts this together with a category on `Amenity`.

- **Found during the build:** the migration is `AddProviderAmenities`. The mapping is in `ProviderAmenityConfiguration`, and the amenities load through `AutoInclude` on `Provider.Amenities`.
