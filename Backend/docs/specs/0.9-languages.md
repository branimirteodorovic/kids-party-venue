# 0.9 Languages

Status: Done
Plan: [0.9 Languages](../implementation-plan.md#09-languages)
Depends on: 0.6 identity (done)

## Goal
Every request knows its language (`sr`, `en` or `ru`), so lookup names can come back translated (1.2) and notifications can go out in each user's own language (2.5). Users get a Domain `UserProfile` that holds this setting and their full name, separate from login data.

## Scope
- In: resolving the request language, `ILanguageContext`, the `Language` enum, the `LocalizedText` value object, the `UserProfile` entity (full name moved from Identity, preferred language), registration creating both records in one transaction, `GET users/me` reading the profile, `PUT users/me/language`.
- Out: the EF mapping and the SQL that picks a translation (1.2, the first table with translated names); setting the language at claim (2.8); sending notifications in it (2.5); changing the full name (no step yet); `Vary` headers for HTTP caching (8.0).

## Acceptance criteria
1. The request language comes only from `Accept-Language`, by quality order, matching `sr`, `en` or `ru` or a more specific tag of them (`en-US`, `sr-Latn-RS`, `sr-Cyrl`). No header, or no supported language in it, means `sr`.
2. Handlers and queries read it through `ILanguageContext.Current`. For a logged-in user it is still the header, not their preferred language.
3. Responses carry `Content-Language` with the resolved language.
4. `LocalizedText` requires Serbian. English and Russian are optional, and a missing or blank one falls back to Serbian when read with `Get(language)`.
5. `POST auth/register` creates the Identity user, its `Parent` role and its `UserProfile` in one transaction: either all three exist afterwards or none do.
6. `POST auth/register` accepts an optional `preferredLanguage`. Without it, the request language is used.
7. `GET users/me` returns `fullName` and `preferredLanguage` from the profile; its response shape is otherwise unchanged.
8. `PUT users/me/language` changes the preferred language. An unknown value returns 400 and changes nothing.
9. Identity's `users` table no longer has a full name.

## API
- `POST auth/register`: new optional field `preferredLanguage` (`"sr" | "en" | "ru"`). The rest is unchanged.
- `GET users/me`: new field `preferredLanguage`.
- `PUT users/me/language`: authenticated, body `{ "language": "en" }`, returns 204. Errors: 400 for an unknown language, 401 when not logged in, 404 `Users.NotFound` when the profile is missing.
- Every response: a `Content-Language` header.

## Data model
- New table `user_profiles` (default schema): `id uuid` primary key and foreign key to `identity.users(id)` with cascade delete; `full_name varchar(200) not null`; `preferred_language varchar(2) not null` (the language code); `created_at_utc timestamptz not null`.
- `identity.users.full_name` is dropped.
- No data is copied, because there is no production data. Local development databases are reset (delete `.containers/db`); the development seeder creates the administrator's profile.

## Edge cases
- `Accept-Language: hr, ru;q=0.5`: `hr` isn't supported, so `ru` is used.
- `Accept-Language: *` or a malformed header: `sr`, never an error.
- `sr-Cyrl`: resolves to `sr`. The API returns Latin text; Cyrillic output isn't planned.
- An English or Russian translation of only spaces counts as missing.
- Registration fails after the Identity user is created (role or profile): the transaction rolls back and no user is left behind.

## Tests
- Unit: `LocalizedText` (Serbian required, fallback per language, blanks treated as missing); the `Language` code mapping both ways; `UserProfile.Create` (name trimmed, required, at most 200 characters) and `ChangePreferredLanguage`.
- Integration:
  - registering with `Accept-Language` `ru`, `en-US,en;q=0.9`, `sr-Latn-RS, en;q=0.5`, `sr-Cyrl, ru;q=0.5`, `hr, ru;q=0.5`, `de`, `*` and no header gives `ru`, `en`, `sr`, `sr`, `ru`, `sr`, `sr` and `sr` in `GET users/me`
  - an explicit `preferredLanguage` wins over the header
  - registration creates the profile with the full name; a duplicate email creates neither record
  - an unsupported `preferredLanguage` at registration returns 400
  - `PUT users/me/language` changes the language, and returns 400 for `de` and 401 without a token
  - `Content-Language` is set on a response
  - the development seeder's administrator has a profile
  - a profile insert that fails after the Identity user is saved leaves no user behind (a test repository that throws)
  - `identity.users` has no `full_name` column

## Decisions
- **ASP.NET Core request localization middleware**, with only the `Accept-Language` provider (no query string or cookie), so the language has a single source. The frontend's interceptor already sends `sr`, `en` or `ru` on every call.
- **Only the UI culture changes per request.** `CurrentCulture` stays invariant, so number and date formatting in code (amounts in IPS QR payloads, SQL parameters, logs) never depends on the caller's language.
- **API error messages stay in English.** FluentValidation's built-in translations are turned off. The frontend translates errors by error code, as its plan says, so localized messages would only make logs and tests inconsistent.
- **`Language` is a Domain enum** (`Sr`, `En`, `Ru`). It is written as `sr`, `en`, `ru` in JSON (`JsonStringEnumMemberName`, with a `JsonConverter` attribute on the enum so any serializer, the tests' included, uses the codes) and in the database (a value converter).
- **Request language and preferred language answer different questions.** The request language is the language of the page being shown right now. Most callers are anonymous parents, every public response is cached per language, and an English page must not get Serbian city names because of a stored setting. The preferred language is for messages sent when there is no page: emails and SMS from background jobs.
- **A Domain `UserProfile` now, holding the full name and the preferred language.** Identity keeps only login data (email, password, lockout, roles, refresh tokens). Putting the language on the Identity user would mean moving it again later; 0.9 is the first step that adds user data unrelated to logging in, so the split happens here. The profile shares the Identity user's ID, and Domain never references Identity: the foreign key is configured in Infrastructure.
- **Registration runs in one database transaction.** `IUnitOfWork` gets `BeginTransactionAsync`; the register handler creates the Identity user (through `IIdentityService`) and the profile (through `IUserProfileRepository`) inside it. This replaces the current compensating delete when the role assignment fails.
- **Changing the language is a normal command slice** (`ChangePreferredLanguageCommand`, repository, `IUnitOfWork`), not a method on `IIdentityService`, which stays limited to login concerns.
- **`LocalizedText` is stored as one column per language** (`<name>_sr NOT NULL`, `<name>_en`, `<name>_ru`), starting in 1.2. The database enforces Serbian, Dapper SQL stays simple (`COALESCE(name_en, name_sr)`), and a fourth language is unlikely.
- **The language is changed with a dedicated `PUT users/me/language`.** There's no profile editing in the plan yet, and a small endpoint is easier to rate-limit and test.
- **Found during the build:** changing your own language needs a new `users:update-self` permission, given to every role, because `users:read-self` is read-only.
- **Found during the build:** in Development, minimal APIs throw on an unreadable request body (malformed JSON, an unknown enum value such as `"de"`), which `GlobalExceptionHandler` turned into a 500. It now answers 400 `General.BadRequest`, the same as other environments, and the 400 is fixed even when the framework reports another status (such as 413) so the code and status always match.
- **Found during the build:** the integration tests still called `auth/...` after endpoints moved under `/api`, so all of them returned 404. The test clients now use `http://localhost/api/` as their base address.
- **Found during the build:** the migration is named `CreateUserProfilesTable`, like the existing migrations, not in the `Underscore_Separated` style the `backend-db-migration` skill describes.
