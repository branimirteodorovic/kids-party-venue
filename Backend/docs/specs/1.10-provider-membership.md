# 1.10 Provider membership

Status: Done
Plan: [1.10 Provider membership](../implementation-plan.md#110-provider-membership)
Depends on: 0.6d permissions, 1.1 cache tags, 1.3 provider entity, 1.9 update provider (all done)

## Goal
A provider knows who owns it. Routes under `providers/{providerId}/...` check that the user owns that provider, so the editor endpoints of 1.9 open to the provider's owners while admins keep access to every profile. Memberships and role permissions are cached per user instead of read on every request.

## Scope
- In: a `ProviderMember` entity (`ProviderId`, `UserId`, `Role`, `JoinedAtUtc`) inside the `Provider` aggregate, with `ProviderMemberRole` holding only `Owner`; `Provider.AddMember` and `RemoveMember` with last-owner protection; the `provider_members` table and its migration; the `ProviderMember` authorization policy (requirement and handler); a cached membership lookup; caching of role permissions in `PermissionService`; a `ProviderMembershipCache` helper (key, tag and expiration, like `LookupsCache`); moving the five 1.9 endpoints from `providers:manage-any` to the `ProviderMember` policy.
- Out: creating a provider and becoming its Owner (1.12); claiming a provider and marking it claimed (2.8); staff (the `Staff` role, invitations, a login per employee, changing roles, an owner-only policy, managing members through the API), which moves to a new post-MVP step P2.16 Staff members; assigning the Identity role `ProviderMember` (1.12 and 2.8, where a user first joins); the provider panel's list of "my providers" (1.12 or the panel step); edit locks by status (1.13).

## Acceptance criteria
1. `AddMember` adds a user as an Owner with `JoinedAtUtc`. A user who is already a member fails with `Providers.AlreadyMember`, and an undefined role fails with `Providers.UnknownMemberRole`.
2. `RemoveMember` on a user who isn't a member fails with `Providers.MemberNotFound`. Removing the only Owner fails with `Providers.LastOwner` and changes nothing. With two owners, either one can be removed.
3. An unclaimed provider created by an admin (1.8) has no members, which is valid.
4. The `ProviderMember` policy succeeds for an Owner of the provider in the route, or for a user with `providers:manage-any`. Any other logged-in user gets 403, including the owner of a different provider. Without a token: 401.
5. A route without a `providerId` route value that parses as a Guid fails the policy (403); the policy never succeeds by default. Today every route that uses the policy has a `:guid` constraint, so such a request never reaches the handler; this criterion has no test (see Decisions).
6. The five 1.9 endpoints use `ProviderMember`. A seeded Owner can read and update their own provider, and the admin still can; a parent and another provider's owner get 403.
7. For a user who isn't an admin, an unknown provider ID returns 403, not 404, so IDs can't be probed. The admin still gets `Providers.NotFound` (404).
8. Memberships are read once per user and cached under `provider-memberships:{userId}` with the tag `user:{userId}`; role permissions are cached under `permissions:{userId}` with the same tag. After `RemoveByTagAsync("user:{userId}")`, the next request reads both again. Later steps that change membership call it after `SaveChangesAsync`.

## API
No new endpoint. `GET /providers/{providerId}` and the four `PUT /providers/{providerId}/...` endpoints of 1.9 switch their auth from `providers:manage-any` to the `ProviderMember` policy. Requests, responses and the other errors stay the same.

## Data model
New table `provider_members`:
- `provider_id uuid`, FK → `providers.id` with cascade (members are deleted with their provider); `user_id uuid`, FK → `identity.users.id` with restrict (deleting a user must not silently remove the last owner); primary key `(provider_id, user_id)`.
- `role varchar(20)` (string enum, `Owner` for now), not null; `joined_at_utc timestamptz`, not null.
- An index on `user_id`, for looking up a user's memberships.

Migration: `CreateProviderMembersTable`.

## Edge cases
- One user can own several providers. This is how an owner with businesses in several categories runs several profiles from one account (the extensibility decision).
- A provider can have co-owners (business partners, through claims in 2.8). Each partner logs in with their own account.
- If a venue shares one account among its staff, each device logs in separately and gets its own refresh-token family, so reuse detection on one device doesn't log the others out.
- A removed owner keeps a valid access token until it expires, but once the tag is removed, the next request reads memberships again; the token carries no memberships.
- An admin who is also an owner: `providers:manage-any` already grants everything, so the membership changes nothing.

## Tests
- Unit: `ProviderMembershipTests` for AC 1–3 (add, duplicate, unknown role, remove, last owner, two owners).
- Integration (`ProviderMembershipAuthorizationTests`): owners seeded through the aggregate and `IUnitOfWork`. An owner reads and updates their provider; another provider's owner gets 403 (AC 4, 6). A parent gets 403 for an unknown provider (AC 7). After an owner is removed and the tag invalidated, the next request gets 403, and role permissions are read again (AC 8). The admin's access and 404, a parent's 403 and the missing token's 401 are covered by the existing 1.9 tests in `GetProviderForEditingTests` and `UpdateProviderTests`. `ProviderPersistenceTests`: members save and load correctly, the composite key rejects a duplicate, and the FK rejects an unknown user.

## Decisions
- **Owners only for the MVP; staff wait until P2.16** (owner's answer). Most venues are small and owner-run; staff management (invitations, roles, removal, a second policy) is real work nobody has asked for yet. Adding `Staff` later is additive: a new string-enum value, an owner-only policy, and the member-management endpoints. Venues that want it now can share one account; what they lose is per-person notifications, audit (1.14) and removing a former employee without changing the password.
- **A membership table, not an `OwnerUserId` column**: users and providers are many-to-many already (one owner, several profiles; co-owners), and 1.12 and 2.8 both write to it.
- **The role column stays**, holding only `Owner`, so staff need no table change.
- **Members are entities inside `Provider`**, as the plan says, so last-owner protection is an invariant of one aggregate and one save. They refer to the user by ID only, as `ProviderAmenity` refers to amenities.
- **Admins pass the policy through `providers:manage-any`**, so the admin panel and the provider panel keep sharing one API (1.9's decision).
- **Non-admins get 403 for an unknown provider**: membership is checked before the handler runs, and a 404 would reveal which IDs exist.
- **The token carries no memberships**: they're looked up through the cache on each request, so removing an owner takes effect without waiting for the token to expire.
- **One cache entry per user** holds all of that user's memberships (provider ID → role). The tag `user:{id}` invalidates it together with the cached permissions.
- **The requirement and handler live in Infrastructure**, next to `PermissionAuthorizationHandler`. The membership lookup is a Dapper read in Infrastructure behind `IPermissionService`, so Application stays free of ASP.NET types.
- **The Identity role `ProviderMember` isn't assigned here**: nothing adds a member through the API yet, and 1.12 and 2.8 assign it when someone first joins.
- **The plan changes in this step's commit**: 1.10 loses `Owner | Staff` and the `ProviderOwner` policy, and P2.16 Staff members is added.
- **Memberships and permissions expire after 30 minutes** (owner's answer), set explicitly in `ProviderMembershipCache.Expiration`: a fallback in case a cache clear is missed, rather than the default from configuration.

- **Found during the build:** `AddMember` and `RemoveMember` take `utcNow` and set `UpdatedAtUtc`, so the provider's `xmin` moves on every membership change. Without that, two co-owners removing each other at the same time could both pass the last-owner check and leave the provider with no owner; now the second save fails with the 1.9 concurrency conflict. `role` is `varchar(20)`, like the other string enums, not `text`. The policy name and the `providerId` route value are constants in `Application/Authorization/AuthorizationPolicies`, so Presentation can reference them. The cache stores a missing user as null, so an unknown user also stays cached until the tag is removed or the entry expires.
- **No unit tests for the authorization handler** (owner's answer): the handler is internal to Infrastructure, and testing it would make the unit tests reference Infrastructure; they stay limited to Domain and Application. The handler is covered through HTTP. A missing or malformed `providerId` (AC 5) is kept out by the `:guid` route constraint rather than proven by a test; the handler still fails closed in that case.
