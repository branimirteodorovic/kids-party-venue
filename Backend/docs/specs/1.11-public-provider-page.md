# 1.11 Public provider page

Status: Done
Plan: [1.11 Public provider page](../implementation-plan.md#111-public-provider-page)
Depends on: 1.1 cache tags, 1.2 lookup data, 1.9 update provider, 1.10 membership (all done)

## Goal
Parents (and search engines, through the SSR frontend) can open a provider's profile by its slug. Only publicly visible providers are shown, and the rule that decides this is written once, so search (3.5), free slots (4.7), inquiries (5.3) and the MCP server (P2.14) reuse it unchanged.

## Scope
- In: a `GetPublicProvider` query slice (Dapper) in `Application/Providers/GetPublicProvider/` with its response records; the endpoint `Presentation/Providers/GetPublicProvider.cs`; the shared visibility fragment `ProviderSql.PubliclyVisible` in `Application/Providers/`; a `ProviderCache` helper (key, tag, expiration, like `LookupsCache`); `RemoveByTagAsync(ProviderCache.Tag(id))` in the four 1.9 update handlers after `SaveChangesAsync`.
- Out: publishing, suspending and the review workflow (1.13; tests set the status directly); photos (3.3); offerings and prices (1.15, 1.16); active offers (P2.15); ratings and reviews (not planned yet); engagement events such as profile views (3.8); invalidation when a category opens or closes in a city (7.7, through the `lookups` tag, see Decisions); search (3.5); the redirect itself, which the frontend does (M7).

## Acceptance criteria
1. `GET /providers/{slug}` for a publicly visible provider returns `200` with the fields under API, anonymously. It never returns status, version, timestamps, members or the claim date.
2. **Publicly visible** means: `status = 'Published'`, `suspended_at_utc IS NULL`, and a `city_categories` row exists for the provider's city and category. The condition is one SQL fragment, `ProviderSql.PubliclyVisible`, written against the alias `p`.
3. A Draft, PendingReview, ChangesRequested or suspended provider, a published provider whose category isn't open in its city, and an unknown slug all return `404 Providers.NotFound`, with the same body, so a hidden profile can't be told apart from a missing one.
4. City, district and amenity names (and the city's locative name) come back in the request language (`Accept-Language`), falling back to Serbian, as in 1.2. Amenities are ordered like the catalog (`sort_order`, `slug`). Name, description and address come back as written.
5. The response carries the city slug and the category, so the frontend can redirect `/{category}/{city}/{slug}` to the canonical URL when the city has changed (1.9) or the URL is wrong.
6. Booking policy and venue details are null while unset (only possible if 1.13 lets such a profile through; today nothing publishes).
7. The slug's provider ID is cached under `provider-slugs:{slug}` (any status, since slugs never change), and the page per provider and language under `provider-page:{id}:{language}`, tagged `provider:{id}` and `lookups`. A miss (an unknown slug, or a hidden provider's page) is removed right after it is read, so a provider that becomes visible shows up on the next request.
8. After any of the four 1.9 updates is saved, the next request reads the provider again in every language. A failed update (validation, 404, 409) removes nothing.
9. A slug with uppercase letters is lowercased before lookup; a slug longer than the column or with characters a slug can't have returns 404 without a database call.

## API
`GET /providers/{slug}`, anonymous, tag `Providers`.
- `200 { id, slug, name, category, description, address, city { id, slug, name, locativeName }, district { id, slug, name }?, latitude, longitude, phone, isClaimed, bookingPolicy, venueDetails, amenities [{ id, slug, name }] }`. `bookingPolicy` and `venueDetails` reuse the shapes of 1.9's `BookingPolicyResponse` and `VenueDetailsResponse`.
- `404 Providers.NotFound`.
- The 1.9 route `providers/{providerId:guid}` keeps priority; a slug never has the shape of a GUID in practice (see Edge cases).

## Data model
No change. The existing unique index on `providers.slug` serves the lookup; `city_categories` has its `(city_id, category)` key.

## Edge cases
- A provider moved to another city (1.9) keeps its slug; the response's new city slug drives the redirect.
- The admin's own Draft isn't visible here even to the admin; the editor uses `GET /providers/{providerId}`.
- Closing a category in a city must hide its profiles at once; 7.7 removes the `lookups` tag when it changes `city_categories`, which drops these entries too.
- A GUID-shaped slug would be routed to the editor endpoint. Slugs come from names (1.4), so one shaped like a GUID is practically impossible; not guarded.

## Tests
- Unit: none new; the handler is SQL plus cache (the slug normalization check is covered through HTTP).
- Integration (`GetPublicProviderTests`, anonymous HTTP): providers created through the aggregate, then published or suspended with a direct SQL update in the test (until 1.13). Happy path with details, policy, district and amenities (AC 1, 5); each hidden case returns the same 404 body (AC 2, 3); names in `sr`, `en`, `ru` and fallback (AC 4); unset policy and details are null (AC 6); a second request after a direct SQL change still returns the cached value, and after `RemoveByTagAsync("lookups")` it doesn't; a hidden provider becomes visible on the next request once published (AC 7); each of the four updates followed by a fresh read (AC 8); an uppercase slug and an invalid slug (AC 9).

## Decisions
- **Suspended profiles are hidden** although the plan names only `Published` and the open category: `SuspendedAtUtc` already exists and suspension is separate from status (1.3), so the fragment has to check it.
- **One 404 for hidden and missing**, so unpublished profiles can't be probed by slug.
- **The fragment is a `const string` in Application** (`ProviderSql`, like `LookupSql`), used by interpolation into raw string literals; every public query in later steps must use it.
- **The cache entry is tagged `lookups` as well as `provider:{id}`**: it holds city, district and amenity names, and opening or closing a category (7.7) is a lookup write. No new `city:{id}` tag is needed.
- **Misses are removed right after they are read**: a provider becoming visible (published, or its city opening) shows up at once, and random slugs can't fill the cache. `ICacheService` has no "don't cache this result" option, so the handler calls `RemoveAsync` on a null; a request arriving in that moment can still get a 404, which is accepted.
- **Expiration is 1 hour, explicit in `ProviderCache`**, like `LookupsCache`; invalidation by tag is the normal path.
- **Two cache levels, slug → ID and ID → page** (changed during the build; the draft keyed the page by slug): tags are fixed when an entry is written, and a request knows only the slug, so a slug-keyed entry couldn't carry `provider:{id}`. The slug map needs no tag, because a slug never changes or moves to another provider (1.4); it expires with `ProviderCache.Expiration`.
- **`BookingPolicyResponse` and `VenueDetailsResponse` move from `GetProviderForEditing/` to `Application/Providers/`**, next to `ProviderVersionResponse`, since two slices now return them.
- **`isClaimed` is public**, so the page can offer "Is this your venue?" to unclaimed profiles (2.8).

- **The phone number is public for now** (owner's answer): it's public business information. Paid plans (6.2) may revisit it, since a visible phone lets parents skip verified inquiries (5.3).
- **The address and exact coordinates are public** (owner's answer): it's a business address, and the map and directions need it.
